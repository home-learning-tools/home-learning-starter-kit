# 基盤のバージョンと配布

コード・AIルール・雛形・demo・テスト・ライセンスを一つの版で配布する。
バージョンの正本は `package.json`。今回の候補は `0.1.5`（予定タグ `v0.1.5`）。
タグ作成前のブランチはリリース済みとして扱わない。

0.xでは互換修正をpatch、API・データ契約の非互換変更をminorにする。
非互換変更には、旧形式からの移行説明を同じPRに含める。
日常利用は固定タグと完全なcommit SHAを指定し、`latest` やブランチ先端へ追従しない。

## 配布物の契約

- `kit/distribution-files.json` は全配布ファイルの明示allowlist。glob・自動追加はしない。
- `kit/distribution-manifest.json` はschema_version=1、version、各ファイルの
  相対POSIXパス・バイト数・SHA-256を保持する。manifest自身だけを一覧から除外する。
- allowlist自身・生成/検証ツール・テスト・文書も一覧に含める。
- 配布内容の変更時はmanifestを再生成して同じPRへcommitする。
  トップレベルを増やす場合はcheckupの許可リスト・文書・テストも更新する。
- 検証は欠落・改変・一覧外ファイル・symlink・特殊ファイルを拒否する。
  ローカル検証で除外するのはトップレベル `.git` と `__pycache__` ディレクトリだけ。
  `workspace/`・`dist/` を含む作業用ツリーは配布できない。
- ハッシュは完全性確認であり、発行者の認証ではない。取り込み側は許可した上流repo、
  タグ、完全なcommit SHA、manifestのSHA-256をlockで固定する。
  タグの移動や取得失敗で自動的に別の版へ切り替えない。
- 下流は取得したコードを実行する前に、自身の検証器でパス・一覧・ハッシュを検証する。
  このツールの成功だけを取得物の信頼根拠にしない。

## 更新とリリース手順

1. 配布内容をレビューし、追加・削除をallowlistへ明示する。必要ならversionを更新する。
2. workspaceや生成物のない専用checkoutで次を実行し、manifestをcommitする。

   ```sh
   python3 -m kit.distribution generate
   python3 -m kit.distribution verify
   ```

3. PRのCIで配布検証・checkup・demo生成を確認する。共通テストは夜間CIおよび
   候補の独立受入検証で実行する。自己レビュー後、利用者の承認を得てマージする。
4. マージ後の完全なcommit SHAを固定し、`git archive <commit>` から空の検証先へ
   展開する。配布検証を先に実行し、次にcheckup・共通テスト・demoと新規workspaceの
   README手順を確認する。検証でできた生成物は配布に含めない。
5. 未使用のタグであることをリモートでも確認し、利用者のリリース承認後に、
   そのcommitを指す `v<version>` タグを作る。既存タグは上書きしない。
6. リリース記録には上流commit、タグ、manifestのSHA-256、検証結果、互換性変更を残す。
   下流はタグが指すcommitも照合してから配布全体を取り込む。

GitHubの可視性変更やPages公開は版の確定とは別判断とする。
公開可視性を変更せずに候補の検証・固定版の配布を進められる。

## 0.1.0候補の変更と移行

- 学習者・教材・テストを含む5正本、相互参照検証、チュートリアル、既存記録の移行支援を含む。
- 旧候補のdemo教材は `examples/demo/materials/shared/` へ移動した。
  独自に旧demoのリンクを参照している場合は変更先を確認する。
- 旧候補に含まれていたサポート外の `PrivateMarkdownAdapter`・`input_contract` は削除した。
  標準形式は `StarterMarkdownAdapter`、独自形式は下流のadapterを使う。
  安定APIは [EXTENDING.md](EXTENDING.md)、入力契約は
  [WORKSPACE-CONTRACT.md](WORKSPACE-CONTRACT.md) を参照する。
- 旧workspaceへ雛形を上書きしない。5正本・列・相互参照を上記契約と照合し、
  退避と変換内容のレビュー後に別workspaceでcheckupを通す。
  移行支援は新規workspace向けで、運用中データの無条件変換を保証しない。

## 0.1.1候補の変更と互換性

- worksheetへ任意の解答配置宣言を追加。未指定は従来どおり別ページ、明示したred-sheetは
  同一紙面の問題・解答と使い方を検証する。赤シート用雛形も配布する。
- 赤シート形式は明示的に閉じた対応HTML構造に限定する。終了タグ省略・不正な入れ子・
  void要素以外の自己終了・未対応要素はエラーにし、ブラウザーと階層が異なる構造を合格にしない。
  対応範囲は [workspace契約](WORKSPACE-CONTRACT.md#htmlワークシートの解答配置) を参照する。
- 既存worksheet・reference・台帳の列・ID・パスは変更不要。自動データ変換は行わない。
- 新しい赤シート教材は旧版coreでは検証できないため、教材採用より先に対応版を導入する。
  旧版へ戻す場合は追加した赤シート教材とその参照も退避し、コードだけを戻さない。
- この記載とversion更新は配布候補の準備であり、タグ作成・リリース済みを意味しない。

## 0.1.2候補の変更と互換性

- 赤シート教材の表示切替等で使うbuttonを対応要素へ追加する。
  同種buttonの入れ子はブラウザーの自動補正を起こすため、終了タグが釣り合っていても拒否する。
- 0.1.1の終了タグ・親子関係・外部依存の制限は維持する。ボタンのJavaScript動作は検査しない。
- この修正だけで外部フォント等を含む教材が移行可能になるわけではない。

## 0.1.3候補の変更と互換性

- 従来の埋め込み教材を維持し、宣言した教材に限ってworkspace内の固定フォントCSSと
  WOFF2を参照できる。manifest、CSSの規則と依存、ハッシュ、symlink・脱出を検査する。
- 任意の外部CSS・JSを許可する変更ではない。共有方式の教材を旧版coreで検証・運用しない。
  下流は本候補の受け入れ後に資産とHTMLを合わせて移行する。
- この記載とversion更新は配布候補の準備であり、タグ作成・リリース済みを意味しない。

## 0.1.4候補の変更と互換性

- テスト予定に既存の実施IDを渡し、Presentationに任意のカード内部表示関数を追加する。
- 既存の引数・未指定時のHTMLを維持する。workspaceのデータ移行は不要。
- 下流が新しい表示関数を使用する場合は本版以降を必要とする。
- この候補の準備は、マージ・タグ作成・リリース承認を意味しない。

## 0.1.5候補の変更と互換性

- 架空demoのダッシュボードをGitHub Pagesへ公開するworkflow（`.github/workflows/pages.yml`）を追加し、READMEからdemoへの導線を張る。
- 公開するのは `examples/demo` から生成した `dist/starter/demo` だけ。利用者のworkspaceや実データは扱わない。
- コード・データ契約・雛形の変更はない。下流のデータ移行は不要。
- この候補の準備は、マージ・タグ作成・リリース承認を意味しない。
